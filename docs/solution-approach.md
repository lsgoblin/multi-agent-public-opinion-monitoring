# 多智能体仿真舆情监测：命题解题思路

本方案面向新版命题《多智能体仿真的保险舆情监测》的**完整要求**，将公开舆情采集、情感识别、证据图、多智能体推演、报告预警、Web 使用、域内运行与评测作为一条连续链路设计。本文独立说明目标方案和验证路径。

## 一、命题解读

要解决的不是单条投诉分类，而是“发现公开事件—理解风险—推演传播—及时处置”的闭环。系统既要能独立运行，也要能接入投诉系统的 AI 溯源模块。命题的各项监测点必须共同完成：

| 链路 | 必须交付与验证的内容 |
| --- | --- |
| 发现与理解 | 合规接入微博、抖音、小红书、黑猫投诉、新闻门户等不少于五个平台；热点采集延迟不超过 15 分钟；负面识别准确率不低于 90%、召回率不低于 85%，情感三分类准确率不低于 88%。 |
| 证据与推演 | 截止时刻之前的来源构成可追溯事件图；独立人设和长期记忆的 Agent 在运行时交互；单事件至少 500 Agent、30 轮，历史事件升级/平息方向一致率不低于 70%。 |
| 输出与响应 | 事件输入后 60 分钟内生成传播、情绪、关键节点、风险、建议五模块报告；给出红橙黄蓝四级预警，红警从发现到实际推送不超过 30 分钟，支持企业微信和邮件。 |
| 使用与交付 | Web 支持任务配置、进度、图谱、看板、报告和带上下文的自然语言追问；Docker 可部署到内网并验证数据不出域；在至少 10—20 件独立真实历史事件上评测，交付部署、接口、使用和测试文档。 |

公开可见不等于可以任意采集或外发。每条来源要记录许可范围、抓取和公开时间、版本与引用；个人信息按最小必要原则处理。历史推演只能使用当时已可见的材料，未来走势仅用于评测。投诉平台样本不能代替公司的全渠道投诉量。

## 二、难点剖析

1. **跨平台时间与身份统一。** 五个平台的接口、内容结构、授权和可见时间证据不同；同一事件会多次转载，不同事件也可能共享关键词。没有可靠的事件身份和时间戳，采集延迟、图谱与回测都会失真。
2. **负面识别与证据归因。** 投诉、转述、辟谣和中性公告容易混淆；少量标签与类别不均衡会造成虚高准确率。报告中的风险判断还必须能回到原始来源及具体 Agent 交互。
3. **真正动态的规模推演。** 500×30 意味着至少 15,000 次决策机会。Agent 的局部观察、独立记忆与运行时消息必须影响后续状态；固定脚本或回放不能证明社会仿真。并发、超时和 Token 预算还会影响是否完整完成。
4. **预测和处置的可检验性。** 历史事件的升级/平息需要先冻结观察窗和标签；报告时效与红警时效分别从事件输入、风险发现计时，离线生成通知不等于送达。
5. **内网可用与合规。** 模型、向量检索、存储、通知和入口网关均可能产生出站流量；仅靠应用日志中的零网络请求，不能证明数据不出域。

## 三、方案选型

采用可分层替换的链路，先保留可验证的输入与输出契约，再逐步接入真实来源和域内资源。

- **采集与事件归并：**为每个平台设置独立适配器，统一为带来源许可、公开时间、采集时间、版本和事件候选 ID 的记录。依据主体、时间、语义和来源关系归并事件，保留人工复核入口；这样既能统计每个平台的实际覆盖与延迟，也能避免把转载当成多件事件。
- **情感与 GraphRAG：**使用独立标注集校准三分类及负面识别；在“事件—主体—来源—观点—时间”关系图上构建截止快照。问题检索同时利用结构化关系和语义召回，答案必须附原文引用、可见时间和图路径；无证据时返回不确定，而不是生成无法追溯的结论。
- **动态多智能体：**为网民、客户、媒体、KOL、监管等角色设置不同目标、局部观察和独立长期记忆。每轮读取截止内图证据、个人记忆与收到的消息，生成动作并写回状态；同步轮次限制“偷看”未来动作。保留消息有无的对照实验，检查交互是否确实改变后续决策。
- **报告与预警：**从同一运行账本生成五模块报告，所有曲线、节点和建议绑定来源及动作引用。四级预警使用可版本化、可回测的规则，再根据真实事件校准阈值；企微与邮件先在沙箱验证载荷、发送和回执，再启用真实通知。
- **工程与成本：**API、Web、任务状态和持久化分离；域内部署使用本地模型与检索资源、受限网络及可审计出口。记录每次模型调用的输入/输出 Token、价格版本和费用，按任务预留预算并设置硬停止；失败或超额后的部分运行只标记为 `partial`。

## 四、步骤拆解

| 阶段 | 目标与产出 | 进入下一阶段的证据 |
| --- | --- | --- |
| 1. 来源与合规 | 确认五平台合法访问路径；统一数据契约、脱敏规则、可见时间和事件身份。 | 各平台可复现采集样本、许可记录、延迟日志及去重人工复核。 |
| 2. 识别与证据 | 建立独立标注集、情感基线、截止快照和带引用 GraphRAG。 | 三分类混淆矩阵、来源引用正确性、未来信息隔离与跨事件隔离测试。 |
| 3. 推演 | 接入域内模型和独立记忆，完成运行时消息传播与 500×30 分级压测。 | 完整有效决策数、消息因果对照、Token/费用账本和失败分类。 |
| 4. 产品闭环 | 接通五模块报告、四级预警、两渠道通知、Web 看板与自然语言追问。 | 真正送达回执、端到端计时、每项结论的来源/Agent 引用及用户操作测试。 |
| 5. 总体验收 | 在域内 Docker 环境回测独立真实事件，冻结评测集并完成四类文档。 | 指标分子/分母、时间边界、流量审计、复现脚本和签收报告齐备。 |

## 五、验证方法

先冻结数据版本、事件身份、评测窗口和人工标签，再按事件划分开发集与留出集；同一事件的多条来源不得跨集合。至少纳入命题要求的 10—20 件**独立**真实历史事件，而不是 10—20 条帖子。每项结果同时报告分子、分母、失败数和排除原因。

| 指标 | 测法与通过标准 |
| --- | --- |
| 覆盖与延迟 | 对五个平台逐一核验合法接入、有效详情和持续采集；以有证据的首次公开时刻与入库时刻计算热点延迟，要求不超过 15 分钟，未知时间单列而不补造。 |
| 情感与负面识别 | 两名独立标注者标注并处理分歧，冻结留出集；用混淆矩阵计算三分类准确率 ≥88%、负面识别准确率 ≥90%、召回率 ≥85%。如“负面准确率”的正式口径未明确，同时报告负面 precision 与二分类 accuracy，待主办方确认采用哪一项。 |
| 动态推演与方向 | 在单件事件执行完整的 ≥500 Agent × ≥30 轮，核对有效决策、记忆读写、运行时消息与预算；用截止前预测和后续真实走势成对评分，升级/平息方向一致率 ≥70%。部分运行不得计作完整达标。 |
| 报告与预警 | 自动检查报告五模块及逐项引用；从事件输入到完整报告 ≤60 分钟。从红色风险发现到企微/邮件成功推送 ≤30 分钟，保存发送和送达回执，`dry_run` 不计入。 |
| Web、成本与域内运行 | 验证配置、进度、图谱、看板、报告和多轮追问；核对 Token 账本与配置上限；Docker 重启后数据一致，并以出口控制和流量观测核实域内数据不外流。 |

## 六、风险与备选

- **平台接口或授权不可用：**优先申请官方接口或合规数据服务；用已获授权的历史材料验证工程，但缺失平台继续记为未覆盖，不以模拟数据充数。
- **可见时间或标签不足：**未知时间的材料不进入历史 cutoff；扩大独立事件和双人标注，保留弃权与争议样本，避免把无分母指标写成达标。
- **规模、质量或费用冲突：**先做 10×3、50×5、100×10 等分级试验，再优化并发、上下文裁剪和模型路由；硬预算或超时触发停止并记录 `partial`，不能用小规模替代 500×30 验收。
- **模型预测不稳定：**与非 Agent 基线做同一事件窗口的对照；不确定时降低预警置信度并交人工复核，保留原始证据与推演轨迹供复盘。
- **通知及内网边界无法验证：**先用沙箱收件人与假数据跑发送链路，完成许可和出口审计后再切换真实渠道；域内部署缺少证据时，只交付本机离线能力并明确边界。
