# 初赛后改进计划

> 2026-10-11 基线。本文是四个开发分支共用的**当前任务与验收依据**，不替代[新版命题](../sources/2026-09-30-新版命题-多智能体仿真舆情监测.md)的指标，也不把计划视为完成证据。实际进度以分支提交、交接和[测试与运行报告](../delivery/test-report.md)的复核结果更新。历史 Day 1—5 规划留在本机归档，不再作为当前排期。

## 当前起点与改进目标

项目已通过初审、进入初赛；目前有可运行的本机离线原型。四个开发分支截至本基线尚无各自的新任务提交。精简源码副本曾全新离线安装并通过 95 项测试；一件真实历史材料案例经离线动态替身完成 10 Agent × 3 轮，产生五模块报告和通知预览。这些是工程基线，不是完整命题验收。

主要缺口是：正式情感、负面识别和走势方向评分均为 **0/0、不可计算**；500 Agent × 30 轮真实模型尝试只有 **3,477/15,000** 个有效决策并以 `partial` 停止；当前 Web 查询不是带上下文的自然语言追问；企微/邮件仅有 `dry_run`；Docker 本机运行已验证，但入口容器仍有默认路由，未证明数据不出域。五平台在线覆盖、采集延迟和完整时效指标也尚无达标证据，详见[测试与运行报告](../delivery/test-report.md)。

历史五日计划把 Day 3 仿真、Day 4 产品与部署、Day 5 综合评测的内部检查点分别称为 **G3、G4、G5**。旧记录中“G3/G4/G5 未通过”只表示这些内部检查条件尚缺证据；它们不是主办方的关口名称，也不否定项目已经通过初审。本阶段按下文的分支条件和新版命题逐项验收，不继续把 Day 编号当作新的开发排期。

本阶段先使每条改进链路**可复现、可评分、可集成**，再依据实测判断完整命题指标。不能用分支数量、事件候选数量、功能页面或测试通过数代替量化验收。目前未给本阶段设定新的截止日期，不把旧五日计划的时间写作新承诺。

## 四分支工作与交付

| 分支 | 本阶段优先工作 | 可由总 Agent 复核的交付 |
| --- | --- | --- |
| `data-evaluation` | 先形成非零正式评分分母：核实来源许可与历史可见时间，冻结独立事件及输入/后续窗口，完成人工标签、预测配对与排除记录；逐步扩展至命题要求的 10—20 件真实历史事件。并行核验五平台覆盖与采集延迟所需证据。 | 事件/来源版本、许可及 cutoff 依据、独立标签与冻结预测对应表、逐单位排除原因、混淆矩阵及每项指标分子/分母。事件身份数本身不算可评分数；AI 标签不作人工真值。 |
| `simulation-scale` | 先用本机离线分级复现超时、并发和内存瓶颈；检验独立记忆和消息对后续动作的作用。在新的模型、数据和费用授权具备后，按冻结配置安排真实模型规模运行。 | 当前提交和配置绑定的逐轮账本：目标/有效/失败决策、轮次、资源、耗时、费用和交互证据。完整 500×30 运行及有效性需单独复核；`partial` 不计为完成。 |
| `product-demo` | 固定获准案例的端到端演示路径，补齐带来源引用和上下文的自然语言追问；清晰区分来源证据图、模拟传播图和离线替身结果。 | 与当前提交一致的操作步骤、截图或录制、案例—图—运行—报告—预警 ID，以及成功、失败、空数据和部分运行的界面验证。 |
| `deployment-alerting` | 从当前提交复现 Docker 构建、运行、重启和持久化；核验全链路出口。继续完善四级预警及通知适配，只有获准的沙箱发送才测试实际回执。 | 源码/镜像/配置版本、健康与重启结果、出口控制和流量观测、通知模式与回执。`dry_run` 不算真实推送；未获授权不发送通知或外部部署。 |

## 验收标准与判定方式

**正式项目验收**以[新版命题的量化目标和验收标准](../sources/2026-09-30-新版命题-多智能体仿真舆情监测.md)为准：不少于五个公开平台、热点采集延迟 ≤15 分钟、负面识别准确率 ≥90% 且召回率 ≥85%、情感三分类准确率 ≥88%、单事件 ≥500 Agent 和 ≥30 轮并行仿真、历史走势方向一致率 ≥70%、事件输入至五模块报告 ≤60 分钟、红色预警从发现至实际推送 ≤30 分钟；还需在命题要求的 10—20 件真实历史事件上验证量化指标，完成 Web、Docker 内网运行、合规溯源及四类文档。成本按可统计 Token、可配置上限和经确认预算核对。各项当前结果及未验证原因见[命题验收清单](../delivery/test-report.md)，不能从某一分支完成推定整体验收通过。

**分支任务验收**是总 Agent 判断能否集成的最低条件，不能代替上述正式指标：

| 分支 | 提交前应达到的可核验条件 | 不计为通过的情况 |
| --- | --- | --- |
| `data-evaluation` | 至少交付一组来源、cutoff、真人标签、冻结预测和后续走势证据可逐单位对齐的合法样本；复跑评分得到非零正式分母，列明混淆矩阵或方向一致率的分子/分母、排除原因。随后按同一规则扩至 10—20 件独立事件。 | 只有事件候选、帖子数量、AI 标签、无后续走势证据或未配对的预测；不能把 0/0 报成 0% 或达标。 |
| `simulation-scale` | 当前提交、模型/替身、配置、数据版本和预算与逐轮账本绑定；相关测试通过，消息/记忆作用及有效/失败决策可追溯。完整规模申请复核时须有单事件 500×30 的完整运行、15,000 次请求机会及有效性、耗时和费用记录。 | 小规模或离线替身外推真实模型能力；超时、预算停止或失败后把 `partial` 写成完整成功。 |
| `product-demo` | 按当前提交从固定案例复现配置、进度、双图、五模块报告、预警和带上下文引用追问；记录 ID 链、当前截图及失败/空数据表现，相关 UI/API 测试通过。 | 旧截图、词项匹配冒充自然语言追问、模拟传播冒充真实平台传播、无证据生成确定结论。 |
| `deployment-alerting` | 当前提交可复现构建、启动、健康检查、任务和重启持久化；逐容器出口有配置与观测记录，四级规则及通知模式、时间戳和回执可追溯，相关测试通过。真实发送/域内结论仅在对应获准环境证据齐备后判定。 | 仅有 `dry_run` 即宣称送达或红警 SLA，通过 Docker 本机功能即宣称数据不出域。 |

分支交接应写实际运行命令、结果、证据路径/版本/哈希、提交号与未完成项；总 Agent 复核差异和证据后决定集成。若只达到部分条件，标为 `partial`，可单独集成已验证部分，但不提高正式验收状态。

## 协作顺序与集成关口

1. **各分支先建立可复核的最小改进。** 从当前共同基线开始，在独立 worktree 内改动自己的范围，记录实际测试和失败。涉及共享 API、schema、数据库、任务状态、模型网关、依赖或总报告时，先向总 Agent 交接契约及兼容性影响。
2. **总 Agent 按证据逐项集成。** 核对分支提交与本机交接，检查差异和敏感材料，运行相关测试及主干回归；把实际改变的结果更新到[测试与运行报告](../delivery/test-report.md)。集成一个分支不自动让其他分支的指标通过。
3. **冻结一次共同演示与评测基线。** 同一提交、来源版本、cutoff、案例/图/运行 ID、模型与预算配置、报告和预警记录应可追溯。对外结果按“代码实现、离线替身、真实运行、正式评分/时效”分别陈述。
4. **最后逐项判断命题验收。** 至少 10—20 件独立真实历史事件及量化报告、完整规模、时效、Web 追问、真实通知和域内边界均须有各自证据；未验证项目保持未验证，不以整体演示替代。

四个分支的工作日志与交接按[协作规则](../../AGENTS.md)保存在主工作区的 `artifacts/branch-work/<branch>/`，该目录被 Git 忽略；本机另有 `artifacts/branch-work/README.md` 说明命名与交接格式。子 Agent 已获所属分支**本地 commit** 授权；此授权不包括推送、合并、额外收费调用、外部采集、真实通知或部署。共享设计和契约见[当前架构与设计依据](../design/当前架构与设计依据-2026-10-11.md)。
